## 根因与整改

在原候选上增加首次挂载后的原生检查，观察到建窗时 `contentMinSize` 为 570 × 440 pt，首次 hosting 布局后变为 0 × 0 pt；对应完整窗口的 `minSize` 为 0 × 32 pt。新增断言在整改前失败，与此前真实拖拽可突破下限的现象一致。

`NSHostingView` 直接作为 `NSWindow.contentView` 时参与更新窗口尺寸边界。Apple 的 [sizingOptions 文档](https://developer.apple.com/documentation/swiftui/nshostingview/sizingoptions)说明了这一行为。本机诊断表明，仅设置空 `sizingOptions` 仍不能保持 AppKit 设置的最小尺寸。

整改将 hosting view 嵌入普通 `NSView` 容器，以宽高 autoresizing 随容器伸展，由现有 AppKit 逻辑独立管理有效最小尺寸。没有改变标准背景、默认内容 570 × 720 pt、常规最小内容 570 × 440 pt、小屏动态下调规则、frame autosave 或屏幕选择逻辑。检查入口也移除重新将 hosting view 直接赋给 `contentView` 的操作。

新增首次布局、错误提示重排、关闭重开后的最小尺寸断言；最终双语结果均保持内容最小 570 × 440 pt，完整窗口最小 570 × 472 pt。本机标题栏高度为 32 pt，其他环境仍由 AppKit 实际换算。
